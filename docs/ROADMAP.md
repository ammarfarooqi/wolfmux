# Limits and roadmap

## Known limits of V1

| Limit | Detail |
|-------|--------|
| Notifications are keystrokes | A notice is typed into a pane, because the recipient is the agent in it and that is the only channel an agent reads. A CLI that is mid-turn queues it; a CLI showing a modal dialog may swallow it. A pane a human is typing in is left alone and the notice waits (up to 10 minutes, 60 s for an approval), so it can be late or, after a long wait, not arrive at all. The 300 ms between the text and the Enter cannot be closed with what tmux reports, so a human who starts typing inside it can still have a keystroke land after a notice. Nothing is lost — the bead stays open in the recipient's inbox — but the agent has to look. |
| Embedded Beads is single-writer | Writers queue on a file lock. Fine for a handful of agents making occasional `bd` calls; a large swarm should use Beads server mode. |
| Comments are silent | Beads fires no hook for `bd comment`. When someone must act, send a message. |
| Same-user trust | Agents are not sandboxed from each other or from the account ([SECURITY.md](SECURITY.md#trust-model)). |
| Workers share `~/.claude` | Plugins, hooks, skills and permissions are common to every Claude-based agent. Deliberate, but a plugin that starts a persistent process from a worker inherits the worker's provider — the reason `claude-mem` is switched off in GLM workers. |
| The worktree guard is pattern matching for shell commands | Exact for file tools; a script or a path built at run time gets past it ([ADR-0016](adr/0016-worktree-guard.md)). Per-worktree git hooks (`reference-transaction`) would close the branch side, at the cost of touching the repository's configuration. Codex workers have no guard. |
| Codex-based agents have fewer guard rails | No `PreToolUse` or `PermissionRequest` hook in Codex: no worktree guard, no lead-approval mode (they fall back to their own prompts or to bypass). Notifications do work, through Codex's `notify` program. |
| Interactive background model ids unobserved | Alias mapping covers them by configuration; only `-p` traffic was observed. |
| Leads of several teams share your checkout | Every lead works in the project root on the branch checked out there; only teammates get worktrees. Two leads that integrate at the same moment get in each other's way. A worktree for a named team's lead would end that, at the price of a lead that no longer sees your uncommitted files. |
| Codex lead permissions are coarse | The rule file allows every `teamctl` and `bd` invocation outside the sandbox (with a prompt on `destroy`). |
| macOS only | Keychain, `/bin/bash` 3.2 paths, `security`, `shasum`. |
| Rare duplicate notification | Two hooks racing over a stale debounce guard can both notify once. |
| A lane parked for days keeps its `node_modules` until someone prunes | `teamctl stop` takes the build caches and deliberately leaves `node_modules`, so a restart stays cheap. Nothing then takes it back on its own: a lane parked for a week holds its 2.3 GB for the whole week unless the lead runs `teamctl prune`. Three things push without anyone remembering — stop takes the caches, remove and `destroy --worktrees` take everything, and `spawn` refuses under `disk-min-gb` with the command to run — but draining by age (stop taking `node_modules` once a lane has been parked longer than some period, or `prune --parked-since <days>`) is the case the original issue is really about and is still missing. |
| `prune` deletes an unignored `build` / `dist` / `target`, where `remove` asks | Those three names are on the cleanup allowlist and are also the ones most likely to hold something a person wrote. `teamctl remove` treats an untracked one that git neither tracks nor ignores as work and asks first; `prune` has no question to ask, so it sweeps the lane and the directory goes. A project that ignores them (the normal case) is unaffected, and one that tracks them is protected by rule 2. Making `prune` skip such a lane instead would be the consistent choice, at the price of `prune` doing nothing at all in a project that neither tracks nor ignores its build directory. |
| `teamctl prune` cannot reach the biggest part of a lane | Measured on one machine: of 25 GB across 38 lane worktrees, about 4 GB sat in a directory on the allowlist. The rest is files git tracks — one project copies 530 MB of `public/` into every lane, about 0.65 GB per lane before an agent installs anything. Rule 2 protects those, correctly, so only `teamctl remove <role>` gives that back. `prune`'s "still held" line prints how much it is, counting the whole of every lane it skipped or left running. |
| A placeholder in a plain colour can look busy | Claude Code draws hint text on its input row dim (`ESC[2m`), and the input-line check ignores dim runs, so an unattended agent pane is never held up by its own hint. That check runs whether or not a client is attached, because a half-typed line survives a detach (issue #9 again, reproduced on a detached session in review round 2). What is left: a placeholder drawn in a plain colour instead of dim (`ESC[38;5;246m` also appears on these panes) reads as typing — now on a detached pane too, not only an attached one — so the notice waits out its cap and is dropped. Every placeholder measured was dim, on this machine's live panes 2026-10-09 and against a real Claude Code in a throwaway socket; Codex is unmeasured. `WOLFMUX_NUDGE_COLLISION_CHECK=0` is the way out. |
| An idle lead with somebody watching another pane is told only by the badge | From v1.15.0 the lead's pane is not typed into while a client is attached, and neither the Stop hook nor `UserPromptSubmit` fires for an agent that is simply sitting idle. So in exactly one shape — a client attached, the human looking at another pane, the lead idle — a bead waits for the `📨` count to be noticed, for the one desktop notification (at most one per role every two minutes, carrying the count), or for the human's next prompt to the lead. Nothing is lost: the bead is in Beads and the notice is in the inbox file throughout. Closing it properly needs a signal nothing provides today — whether a CLI is at its prompt or mid-turn — so the alternatives are all guesses at that from the pane's pixels. `WOLFMUX_NUDGE_TYPE=all` is the way out for anybody who prefers the old noise. Staying silent in the conversation is the settled default, so this is a known and accepted limit rather than an open question. |
| Two bead-less notices inside the debounce count as one | One logical Beads change fires several hooks, so `inbox_add` does not file a record identical to the last one within `WOLFMUX_NUDGE_DEBOUNCE` (3 s) — otherwise the `📨` count would read 3 for one bead. A notice that carries a bead id is unique, so nothing real is collapsed there. The bead-less form (`_nudge_text` with no id) prints the same line for any bead, so two **different** beads arriving inside that window count as one and the badge reads 1 where two arrived. The same trade-off the existing nudge already makes, for the same reason: that line ends with the agent's full inbox command, so one notice genuinely covers both beads and the agent sees both. |
| The envelope is blank for a few seconds after you attach | tmux draws a status line BEFORE the `#()` job behind it has produced anything, and fills the segment on a later refresh — measured on 3.7c, where the same run rendered the segment first empty and then with its output. So on every client attach, and after every tmux server restart, the `📨` count is missing for up to `status-interval` (5 s) before it appears. Somebody attaching to a team with three notices waiting sees no envelope at the exact moment they look. It is inherent to how tmux runs `#()` — the alternative is teamctl writing the segment's text into the option itself on a timer, which means a process per team per interval — so it is written down rather than fixed. No notice is lost, and `teamctl inbox` is correct the instant it is run. |
| The badge appears only for teams started after the upgrade | `status-left` is read when the tmux server starts, and `@wolfmux_teamctl` is set when a team starts, so a session already running when v1.15.0 is installed shows no count. `teamctl inbox` reads the file regardless, and the next `teamctl start` of that project fixes it; nothing detects the case and says so. |
| The anti-glue numbers bound one check only | The "5 of 5 down to 2 of 5" figure for re-checking between queued lines was measured with a watcher typing through `tmux send-keys`, which does not move `#{client_activity}`. So it bounds the input-line check alone and says nothing about the keystroke check, which a real person also trips. A harness that pushes keystrokes through an attached client's own stdin would measure the real thing; one attempt deadlocked. What is confirmed either way: no notice is ever delivered twice and none is lost. |
| One background waiter per approval request, with no cap | `_inbox_approval_grace_start` copies the nudge waiter's detachment (subshell, `trap '' HUP INT TERM`, no setsid) but NOT its pending marker, which is what keeps that one to a single waiter per role. So every permission request gets its own waiter, and each runs one `jq` against the approvals store plus one tmux read per second for the length of the grace. Five workers asking at once is ten processes a second for 20 s, and they then pile onto `nudge_begin`'s spin. Nothing is lost — the losers park and the badge carries them — but a human who raises `WOLFMUX_INBOX_APPROVAL_GRACE` to a few minutes because 20 s felt noisy pays for it in processes, with no cap and no reap. Left as it is deliberately: a marker keyed by role would make a second request wait for the first request's grace to end, and two blocked workers are exactly what must not be serialised. A cap would need a rule for what to do at the cap, and that is a behaviour decision, not a tidy-up. |
| `tests/docs.sh` guards what the docs NAME, not what they COUNT | It asserts that the documentation names every command, option, policy key, model and setting the code has — which is why a doc claiming behaviour the code does not have gets caught. It checks neither suite names nor any number. Two consequences, and both were live in this repository until v1.15.0 swept for them by hand: a NEW test suite can be added without any doc check noticing that the one place listing the suites (`README.md`, the `tests/` row) does not mention it; and every check count in the docs is unguarded, so a count goes stale the moment a suite grows and nothing says so. A grep for placeholder tokens does not find these either — a live number that has quietly become wrong looks exactly like a correct one. The root of the second consequence is that nothing in the repository runs the suites as a set: there is no runner, no build file and no CI, so every lane that gates this branch writes its own wrapper and enumerates the suites by hand, the only other enumerations being two prose lists — `README.md`'s `tests/` row and `docs/VERIFICATION.md`'s re-run block — which already disagree with each other, so a newly added suite is absent from every wrapper and from both lists until each is updated separately, and no canonical total exists for any doc to be checked against. Closing it splits into a cheap half and an expensive one, and the split is the useful part. The CHEAP half is not checking suite names: it is asserting that every count in the docs is ACCOMPANIED BY the name of the suite that produces it, **without verifying the number at all**. That alone would have caught the stale count above, because the row would then have had to be touched by any release that changed that suite — and the real failure mode is a release changing a suite and never visiting the row, not a release getting the arithmetic wrong. The EXPENSIVE half is making the number itself right, which means parsing checks out of each suite rather than trusting a summary line. Neither was attempted inside an otherwise-finished release. Until one is, treat "a count appears in prose" as a smell and sweep bare numbers as well as tokens whenever the suites change. |
| A check that asserts a signal disposition needs a skip path for EVERY signal a detached launch can leave ignored | An inherited `SIG_IGN` cannot be undone from inside the process, so a check that sends itself a signal and expects to die from it cannot hold when the launch already ignored that signal. v1.14.2 established the right answer for one signal: `smoke.sh`'s SIGHUP check SKIPS, with the reason printed, instead of reporting a bare FAIL. Its SIGINT sibling one line above has no skip path, so the same situation makes it FAIL — and a background job from a non-interactive shell inherits SIGINT *and* SIGQUIT as `SIG_IGN`, on top of the SIGHUP `nohup` ignores. Every agent on this machine launches suites detached, so every such lane sees a red check that is not a defect, which is how a failure nobody owns becomes permanent. A harness can reset the dispositions in a parent that then `exec`s the suite — v1.15.0's gate wrapper does exactly that, for HUP and INT both — but a harness fix protects only the lanes that know about it, and the check itself still cannot tell "the code is broken" from "this signal was ignored before I started". The general form, which is what makes this worth recording rather than patching: for each signal a check depends on, it has to detect that the signal arrives already ignored and skip with a printed reason, exactly as the SIGHUP one does. Not fixed here: the check and its skip pattern belong to the release that introduced them, and widening a sibling's contract inside an unrelated release is how two releases end up owning one check. |

## What a V2 could be

The original plan was "V1 on files, V2 on SQLite". Adopting Beads made that moot:
tasks and messages already live in a versioned database, and `teamctl`'s own
registry is a few small JSON files behind one module. Candidates that would solve
real problems, in the order they are likely to matter:

1. **Beads server mode, opt-in per project** — when lock waits become noticeable.
   `teamctl start` would own starting and stopping the Dolt server; the design
   constraint "no daemon" would have to be relaxed knowingly.
2. **Delivery confirmation** — have the notice carry a token the agent acknowledges
   with `bd`, so the lead can see which notifications were actually read.
3. **A reviewer role preset** — `teamctl spawn reviewer astra` already works; a
   protocol section and a task template for "second opinion" reviews would make it
   routine.
4. **Per-role settings overlays**: the provider overlay mechanism generalised to any
   role (for example a QA worker with a narrower tool allow-list).
5. **Linux support** — a secret-service backend instead of the macOS Keychain.
6. **Finer Codex rules** — allow read-only `teamctl` subcommands silently, prompt
   on the mutating ones.

Not planned: an MCP server, a web UI, a daemon, and the metered aggregators and
proxies (OpenRouter, LiteLLM, Fireworks, Novita, SiliconFlow: forbidden by
[GOALS.md](GOALS.md#hard-constraints), before and after v1.10). The direct metered
providers (the Moonshot platform, DeepSeek) exist since v1.10, gated behind
`WOLFMUX_METERED`, off until the owner sets it.
