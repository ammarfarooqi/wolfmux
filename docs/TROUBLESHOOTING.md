# Troubleshooting

Start with `teamctl doctor`, then `teamctl status`, then `teamctl capture <role>`.

| Symptom | Cause | Fix |
|---------|-------|-----|
| teammates appear in extra terminal panes and ask a *worker* for approval ("Waiting for team lead approval") | the worker used Claude Code's own agent-teams feature (your settings enable it), which makes the spawning session a team lead | fixed since 1.1: teamctl switches that feature off inside workers. Restart workers started with an older version: `teamctl restart <role>` |
| a provider worker (GLM, Kimi, DeepSeek, MiniMax, Qwen) starts with `Both CLAUDE_CODE_OAUTH_TOKEN and apiKeyHelper set · auth may not work as expected` | that variable is the login guard: an inert value that keeps a provider worker (and anything it starts) from ever falling back to your claude.ai login | expected and harmless: `apiKeyHelper` takes precedence, so that provider's key is what gets sent. It is not the cause of a 401 that appears next to it: run `teamctl doctor --probe` for that. Do not unset either ([why](SECURITY.md)) |
| clicking a "task complete" notification opens **Script Editor** | the notification was sent with `osascript`: by an agent started before 1.3, or on a machine where `Wolfmux.app` was not built | `./install.sh` builds `~/.config/wolfmux/Wolfmux.app` (needs `osacompile`, part of macOS); then `teamctl restart <role> --continue`. From 1.5 a click opens the team whether or not it is on a screen |
| no notification while the team is detached | macOS has not been told to allow notifications from Wolfmux | System Settings → Notifications → Wolfmux → allow. Test: `cd <project> && echo '{}' \| TEAM_ROLE=lead teamctl _notify` |
| clicking a notification does nothing, or a prompt about "control iTerm" was denied | Wolfmux.app may not send Apple events to the terminal | System Settings → Privacy & Security → Automation → Wolfmux → enable iTerm (or Terminal) |
| no notification at all when an agent finishes | `WOLFMUX_NOTIFY` is `off` or `lead`; or iTerm2 is not allowed to notify; or that tab is the one in front (iTerm2 stays quiet then) | check `~/.config/wolfmux/config`; macOS Settings → Notifications → iTerm2; iTerm2 → Settings → Profiles → Terminal → "Notification Center Alerts" |
| `teamctl start fable` opened the running Astra team instead of a new one | before 1.8 a project had one team, and `start` attached to it | from 1.8: `teamctl start fable --team <name>` starts a second team; without `--team`, `start` refuses to hijack a team led by another model and prints both commands |
| `this project has several teams (…); say which one` | a command typed at your terminal cannot guess | add `--team <name>` (before or after the command). `teamctl status` and `teamctl teams` show them all |
| in a named team with `worker-permissions lead`, permission requests appear at the first team's lead, or the teammate's own prompt appears at once | before 1.9 the permission hook filed every request with the first team | `./install.sh`, then `teamctl restart <role> --continue --team <name>`. Requests now go to that team's own lead (`teamctl approvals --team <name>`) |
| `WOLFMUX_APPROVAL_TIMEOUT` in `~/.config/wolfmux/config` changes nothing | before 1.9 it was read before the config file was loaded; only the environment variable worked | `./install.sh`; agents started afterwards wait as long as the file says |
| `./uninstall.sh --purge` says KEPT although no worktree is left | before 1.9 the empty `teams/` folder of a named team counted as one | update the checkout and run it again |
| a team should be gone completely and give its disk space back | `destroy` keeps worktrees on purpose | `teamctl destroy --team <name> --purge`: shows sizes and any uncommitted or unmerged work, asks, deletes. `--force` deletes that work too |
| `teamctl destroy` ran, but `teamctl status` still lists stopped workers | `destroy` keeps worktrees; `destroy --worktrees` removes only workers that hold nothing (clean, merged) | `teamctl destroy --worktrees` for the clean ones. One that still holds work: `git merge <branch>` to keep it, or `teamctl remove <role> --force` to discard it |
| every worker commit fails a pre-commit rule about the branch name, so workers commit with the project's skip switch or `--no-verify` | worker branches are `ai/<role>-<timestamp>`, which carries no ticket key | from 1.11: `teamctl policy branch-template 'feature-{ticket}-{role}-{ts}'`, then spawn with `teamctl spawn <role> <model> --ticket <KEY>` (or give the whole team one: `teamctl start <model> --ticket <KEY>`). One worker, one name: `teamctl spawn <role> <model> --branch <name>`. Existing workers keep the branch they have; re-spawn them to get a conforming one |
| `the branch template of team '<x>' is '…', so this spawn needs a ticket key` (exit 64) | the template has `{ticket}` in it and neither the spawn nor the team supplied one | add `--ticket <KEY>` to the spawn, or `teamctl start <model> --ticket <KEY>` for the team. teamctl never invents a ticket key, because a wrong one is what the template exists to prevent |
| `every template needs {ts}` or `unknown placeholder {…}` (exit 64) | a branch template that cannot produce unique names, or a typo | `{ts}` is required; the known placeholders are `{team}` `{role}` `{ts}` `{ticket}`. `teamctl policy` shows the current one, `teamctl policy branch-template default` restores the built-in shape |
| `branch '<name>' already exists in <repo>` (exit 1) | `--branch` named a branch that is already there | wolfmux never adopts a branch it did not create, because `teamctl remove` deletes a worker's branch. Choose another name |
| `teamctl remove` said `teamctl did not create branch '<name>'; it was left alone` | the record's branch was not made by teamctl (an edited record, or a branch of your own) | intended: only a branch teamctl created is ever deleted. Delete it yourself if you want it gone: `git branch -d <name>` |
| work spans several repositories and the only way through was `teamctl policy worker-isolation off` | before 1.11 a team could only work inside its own project | from 1.11: `teamctl spawn <role> <model> --repo ../other-repo` puts that worker's worktree and branch in that repository with the guard still on. Switch isolation back on: `teamctl policy worker-isolation on`, then `teamctl restart <role> --continue` |
| a `--repo` worker cannot see its Beads inbox | `bd` resolves its workspace through git, and that worker sits in another repository | fixed in 1.11: teamctl sets `BEADS_DIR` for such a worker to the project's own workspace. Older worker: `teamctl restart <role> --continue`. Check with `teamctl capture <role>` |
| `--repo: … is not inside a git repository` or `has no commits yet` (exit 64) | the path is not a git checkout, or a fresh `git init` with nothing committed | point `--repo` at a checkout with at least one commit; a worktree needs a commit to branch from |
| a worker reports `Wolfmux: … is outside your worktree` or a refused shell command | the worktree guard: teammates may not change anything outside their own worktree and branch | intended. The worker should ask the lead. If a legitimate command keeps being refused: `teamctl policy worker-isolation off`, then `teamctl restart <role> --continue` |
| `teamctl start` showed a window full of `Pane is dead` | before 1.4: every agent had been quit, tmux kept the finished panes, and `start` attached to them | fixed in 1.4: `start` clears a session in which every agent has exited and opens a new one; a lead that exited alone is brought back in place. Older install: `teamctl destroy`, then `teamctl start` |
| the panes are arranged badly for your screen | default is the lead on the left at 55 % | `teamctl layout lead-top` or `teamctl layout tiled`; `Ctrl-b Space` cycles; drag a border with the mouse; `Ctrl-b z` zooms one pane |
| the wolf popup is in the way | it shows on every attach | any key closes it; `WOLFMUX_SPLASH=off` in `~/.config/wolfmux/config` removes it from the next attach on |
| 🐺 shows as a box or misaligns a border | the terminal font has no emoji fallback, or counts its width differently | use a terminal with emoji support (iTerm2, Terminal.app, kitty, Ghostty, WezTerm all do) |
| a worker shows a long yellow `"glm-5.3" isn't described by this version's model catalog …` | Claude Code does not know GLM's model ids and announces the 200k window it assumes | fixed in 1.4: `claude-glm` declares that window (`CLAUDE_CODE_MAX_CONTEXT_TOKENS=200000`), which removes the notice and changes nothing else. Restart the worker: `teamctl restart <role> --continue`. Another window: `WOLFMUX_GLM_CONTEXT=<tokens>` or `1m` |
| an Astra (Codex) agent says `Code Mode is unavailable … codex-code-mode-host: host executable was not found` and cannot run any command | Codex was started through a symlink and looked for its helpers next to the symlink | fixed in 1.7: `./install.sh` replaces the `~/bin/codex` symlink with a wrapper, and `codex-astra` starts the real file. Then `teamctl restart <role>` |
| the lead answers "spawn a teammate" by opening a terminal or a subagent | it did not connect the request with `teamctl spawn` | say "run `teamctl spawn <role> <model>`"; from 1.7 the protocol spells that out. A lead started earlier: `teamctl restart lead --continue` |
| a worker's banner says `API Usage Billing` | Claude Code's label for any key-based login | expected for GLM workers: the key is the Z.ai Coding Plan key, the endpoint is Z.ai's. Check `/status` in the pane |
| after a reboot (or after tmux was ended) `teamctl restart <role> --continue` says the team has no session | the tmux session is gone; the records, worktrees and conversations are not | `teamctl restart lead --continue --team <name>` starts the team again in the lead's last conversation (from 1.10.1; before that it pointed at a bare `teamctl start <model>`, which opens a new conversation). Then `teamctl restart <role> --continue` for each teammate |
| several leads of one project come back on the SAME conversation after `--continue` | before 1.12 `--continue` meant `claude --continue`: the newest conversation in the folder. Every lead of a project works in the same folder, so they cannot be told apart | `./install.sh`, then re-seat each lead on its own id: `teamctl restart lead --team <name> --resume <session-id>`. From 1.12 every agent is started with its own id and `--continue` reopens that one. The ids of live agents are in `~/.claude/sessions/<pid>.json`; stored ones are in `teamctl status --json` |
| a pane says `nothing to continue yet: conversation … has no transcript` | `--continue` for an agent that never said a word. The CLI writes a transcript only once something was said, and refuses to resume an id without one | nothing to do: the conversation is started fresh under the same id, with its kickoff if it had one |
| `--resume: no conversation <id> under ~/.claude/projects` (exit 1) | the id you named has no transcript in any folder (a typing mistake, or the conversation was deleted) | `teamctl status --json` prints each agent's stored id; your own are the file names in `~/.claude/projects/<folder>/` |
| `--resume: conversation <id> is the one '<agent>' has on record` (exit 1) | you named the conversation another agent of this project already has; two agents in one conversation write over each other | name the right one (`teamctl status --json`), or restart that other agent on its own first |
| a status line shows the CONTEXT of another conversation, or `-` for a lead that has been working | before 1.12 CONTEXT was read from the newest transcript in the agent's folder, and every lead (and your own sessions) share the project's folder; `-` means the agent's own conversation has no transcript yet, or its record has no id | from 1.12 it is read from the agent's own conversation by id. An agent from before: `teamctl restart <role> --resume <session-id>` |
| `teamctl restart <role> --continue` warns `no stored conversation id` | that agent was started before 1.12 (or the team was started with `--continue` and had no conversation on record), so its record has no id | harmless: it falls back to the newest conversation in the folder. Give it one with `--resume <session-id>`, or let the next plain `restart` mint a fresh one |
| a worker stalls on a permission prompt | it runs in `ask` mode, or a lead-mode request timed out | `teamctl status` shows its PERM column. `teamctl policy worker-permissions skip` (or `lead`), then `teamctl restart <role> --continue` |
| `'teamctl …' is reserved for the lead` (exit 77) | a worker tried a manager command, or tried to spawn while `worker-spawn` is off | intended. The worker should message the lead; you can allow spawning with `teamctl policy worker-spawn on` |
| a lead is refused (exit 77) on a team it founded, and the message says `you founded it: once its lead has stopped …` | the founded team's lead is still running: while it runs, its founder does not manage the team | intended. Message that lead (`bd create … -a <team>.lead`). Once its lead is not running the founder may `restart`, `stop`, `remove` and `destroy` the team ([when the lead of a founded team is gone](USAGE.md#when-the-lead-of-a-founded-team-is-gone)) |
| the lead of a founded team died and nobody could restart, stop or delete the team | before 1.11 only you could: a founder was refused whatever state the team was in (GitHub issue #2) | from 1.11 `teamctl teams` marks such a team `orphaned` and names who may act; its founder runs `teamctl restart lead --team <name> --continue` or `teamctl destroy --team <name> --purge --force`, and you are told. A team founded before 1.11 keeps its founder in the lead's record, so it works too |
| after a restart without a session a founded team lost its handover, or its founder | before 1.11 that restart wrote the lead's record again from nothing | from 1.11 the handover, the founder and the creation time are kept |
| `teamctl restart lead …` after a reboot stops with `Beads (bd) is not installed` | `bd` is not on the PATH of that shell; a project that merely has no Beads workspace is still started without one | install or expose `bd` (`teamctl doctor`), then run it again; for a project that never used Beads, `teamctl start <model> --team <name> --continue --skip-beads` |
| `teamctl: command not found` | the `~/bin` PATH block is not loaded yet | open a new terminal; check for the `>>> wolfmux >>>` block in `~/.zshrc` |
| worker pane says `no Keychain item for service 'zai-coding-plan'`, state `exited(78)` | the Z.ai key was never stored | run the `security add-generic-password …` command the pane shows, then `teamctl restart <role>` |
| GLM worker answers with 401 / authentication errors | the key is wrong or expired (the usual case), or the endpoint rejected helper-mode headers | run `teamctl doctor --probe`: a FAIL line names the Keychain slot; re-store the key (the same command, `-U` overwrites) and `teamctl restart <role>`. Only if the probe accepts the key, set `WOLFMUX_GLM_AUTH_MODE=env` in `~/.config/wolfmux/config` as a last resort |
| GLM worker reports `1113 Insufficient Balance` | the call fell outside the Coding Plan (wrong endpoint or a non-plan model id) | `WOLFMUX_DRY_RUN=1 claude-glm` must show `https://api.z.ai/api/anthropic` and a `glm-5.3*` model; check the plan is active on the account that issued the key |
| a provider worker pane says `no Keychain item for service 'wolfmux-…'`, state `exited(78)` | that provider's key was never stored | run the `security add-generic-password …` command the pane shows (all six: [SETUP.md](SETUP.md#3-the-keys)), then `teamctl restart <role>`; `teamctl doctor` says which providers are set up |
| `teamctl spawn` / `teamctl start` refuse a `moonshot` or `deepseek` model (exit 77), or the launcher exits 78 naming `WOLFMUX_METERED` | the metered gate: those two bill per request, so they start only when both the key is stored and `WOLFMUX_METERED=on` is in `~/.config/wolfmux/config` | decide at your terminal whether per-request billing is what you want, add the line yourself, then `teamctl restart <role>`. An agent that asks you to flip the switch should be refused |
| a moonshot / deepseek / minimax / qwen worker answers 401 | the key is wrong, expired, or of the wrong kind for that endpoint (a Qwen key must be a Coding Plan key, `sk-sp-`) | run `teamctl doctor --probe`: it says `the key in 'wolfmux-<p>' is rejected by <endpoint>` and where that key comes from; re-store the right one, then `teamctl restart <role>`. Changing the auth mode does not help against a rejected key |
| a kimi worker answers 401 (`The API Key appears to be invalid or may have expired`) although `teamctl doctor` said ok | the key in `wolfmux-kimi` is a Moonshot platform key (created at platform.kimi.ai). The `kimi` endpoint accepts only a Kimi Code membership key (Kimi Code console, starts `sk-kim`); plain doctor only checks that the item exists | `teamctl doctor --probe` shows the FAIL and warns that the key does not start with `sk-kim`. Store a Kimi Code membership key in `wolfmux-kimi`, or keep the platform key and use the `moonshot` provider (metered), then `teamctl restart <role>`. `WOLFMUX_KIMI_AUTH_MODE=env` does not help |
| a kimi worker started in `env` mode stops at `Detected a custom API key in your environment ... Do you want to use this API key?` and never proceeds | `WOLFMUX_KIMI_AUTH_MODE=env` exports `ANTHROPIC_API_KEY`, and Claude Code asks before using it; the default answer is No, an unattended worker waits, and Claude Code documents no setting that pre-approves the key | go back to helper mode (remove the line from `~/.config/wolfmux/config`, `teamctl restart <role>`), or answer Yes once in the pane (`teamctl focus <role>`; Claude Code remembers the choice). Env mode cannot fix a rejected key: `teamctl doctor --probe` |
| `teamctl doctor --probe` warns `does not start with 'sk-kim'` (or `'sk-sp-'`), or says `no answer` | the stored key looks like another vendor console's key; or this machine is offline or the endpoint is down, so the key was not checked | the warning names the console the key should come from; store that key. For `no answer`, check the network and run it again |
| a provider worker announces an unknown model id, or the vendor renamed its models | the default ids in `lib/providers.sh` are older than the vendor's page | pin the ids yourself in `~/.config/wolfmux/config`: `WOLFMUX_<P>_MODEL` and `WOLFMUX_<P>_FAST_MODEL` (GLM is not pinnable), then `teamctl restart <role>` |
| a new worker sits on "Do you trust this folder?" | first time this repository is opened with that CLI | answer it once in the lead pane; Claude Code keys trust on the main checkout, so worker worktrees inherit it |
| `spawn --from-worktree <role>` exits 1 and lists files | the handed-over worktree has uncommitted changes; they would land uncommitted on the new worker's fresh branch | commit them in that worktree first (`git -C <worktree> status` to see them), or discard them; then run the spawn again |
| `teamctl status` shows `-` in the CONTEXT column for an agent that has been talking | status reads what the CLI wrote to disk, and finds nothing it can parse: the agent has made no assistant turn yet, its transcripts folder sits elsewhere (`WOLFMUX_CLAUDE_PROJECTS`, `WOLFMUX_CODEX_SESSIONS`), or (codex) the rollout's session cwd does not match the worktree | check the paths; for codex, only a rollout whose session started in the worktree is matched. `-` is never an error and never blocks a command |
| a worker never reacts to a message | its CLI was showing a dialog, or the hook is missing | `teamctl nudge <role>`; `teamctl doctor` must say the pane-notification hooks are installed (`teamctl start` reinstalls them) |
| the notice has not arrived yet, and `teamctl nudge` said `deferred` | the message names the check that fired: the input line is not empty, copy mode, or a keystroke seconds ago. The notice is parked and arrives by itself. The input-line check applies whether or not a client is attached, because a half-typed line survives a detach | clear the input line (or leave copy mode) and it comes within a few seconds. `ls ~/.wolfmux/state/*/nudge/` shows a parked `<role>.pending`; at the cap (10 minutes, 60 s for an approval) it is dropped and `events.jsonl` says `nudge-defer-expired`. A marker left by a waiter that died is reaped by the next nudge (`nudge-defer-reaped`). `WOLFMUX_NUDGE_COLLISION_CHECK=0 teamctl nudge <role>` types it in regardless |
| inbox looks empty although a message was sent | message beads are hidden by default | add `--include-infra`: `bd list --assignee <role> --status open,in_progress,blocked --include-infra`. Note that `teamctl inbox` is a different thing — the short pane notices, not the work |
| `teamctl nudge` said `filed` and nothing appeared in the lead's pane | that is the v1.15.0 behaviour, not a fault: your lead pane is your conversation, so while a client is attached to the team a notice is filed instead of typed | `teamctl inbox` (or `prefix N`) shows it; the `📨` count on the left of the status line counts what you have not expanded. The agent is given it by its own hook when its turn ends or when you next prompt it. `WOLFMUX_NUDGE_TYPE=all` brings the old typing back everywhere |
| the `📨` count is missing for a few seconds right after I attach | not a fault: tmux draws the status line before the `#()` job behind the badge has produced anything, and fills it on a later refresh | it appears within `status-interval` (5 s). Nothing is lost and no notice is affected; `teamctl inbox` is correct the instant you run it. The same applies after a tmux server restart |
| the `📨` count is not in the status line of a team that was already running | the running tmux server is still using the `status-left` it was given before the upgrade — the new config has not been read into it yet | `tmux -L wolfmux source-file ~/.config/wolfmux/tmux.conf` applies the badge AND the new key bindings to the running server at once. No server restart, and **no team restart** — do not restart a team for this, it regenerates every agent's settings document. Every setting in that file is a `set -g` overwrite, so re-sourcing is safe to repeat. It re-sources your own `~/.tmux.conf` too (see the row below), which is why a wolfmux binding always wins inside that server. Nothing is lost while you wait: `teamctl inbox` reads the file regardless |
| the `📨` count stays blank after sourcing the config | tmux runs what a format names through `/bin/sh` with whatever PATH the **server** was started with, so a server whose PATH has no `teamctl` in it finds nothing — and the badge swallows every error by design, so it shows nothing rather than complaining | a session started by `teamctl start` is unaffected, because it carries teamctl's absolute path in `@wolfmux_teamctl`. | a lane says a package is missing, right after a `prune` or a `stop` | `prune` takes `node_modules`, `stop` takes the build caches | in that worktree: `npm install` (or the project's own install command). Nothing else of the lane changed |
| a `.wolfmux-removing-*` directory inside a worktree | a cleanup was killed halfway (the disk filled, the machine rebooted) | harmless; the next `teamctl prune` / `stop` / `remove` clears it. By hand: `/bin/rm -rf` that one directory |
| `teamctl prune` says "skipped: it has untracked files that are not build output (X)" | the lane holds something that is not regenerable, so nothing of it is touched | look: `teamctl diff <role> --working`. Keep it: commit it in that worktree. Let the lane go: `teamctl remove <role>` |
| `teamctl status` says "this team's lanes: not measured" | status never runs a `du` (over 36 lanes that is 12 s); it reads the number the last command left | `teamctl teams` measures it |
| `teamctl prune` refuses: "cannot tell whether '<role>' is running" | its record says the agent is running and the team's tmux session shows no pane for it. prune sweeps lanes unattended, so it stops rather than guess | `teamctl status` and `teamctl panes` to see which is right, then `teamctl stop <role>` (park it for real) or `teamctl restart <role>` (bring it back), and run prune again |
| `teamctl policy disk-min-gb 08` is refused | a leading zero is ambiguous: shell arithmetic would read `08` as octal and `010` as 8 | write it without the zero: `8`, `10`, `20` |
| `teamctl prune` says "still held … is in files git tracks" | most of a lane is the checkout itself, not build output — one project copies 530 MB of `public/` into every lane | nothing to fix; `teamctl remove <role>` is the only thing that gives that part back |

## The disk is full

```bash
df -h /                                  # how bad it is
du -sk ~/.wolfmux/worktrees/* | sort -n  # which project's lanes are the problem
teamctl prune --dry-run                  # in that project: what the parked lanes hold
teamctl prune                            # take it (node_modules and all build output)
teamctl teams                            # what each team still takes
teamctl destroy --team <name> --purge    # a team you are finished with, worktrees and all
```

Each lane worktree carries its own `node_modules` and build output — 2-3 GB is normal for a
Next.js project — and a parked lane keeps all of it until the role is removed. `prune` only
touches lanes that are not running and never anything git tracks or any uncommitted work.
If a lane is skipped and you need the space, `teamctl remove <role>` takes the whole
worktree (it refuses while the lane holds work that exists nowhere else; `--force`
discards it after one question). To stop it happening again:
`teamctl policy disk-min-gb 40` raises the bar a spawn has to clear, and
`teamctl policy link-node-modules on` makes new lanes share the project's `node_modules`
instead of installing their own.

## Tab completion

| Symptom | Cause | Fix |
|---------|-------|-----|
| `teamctl <Tab>` offers nothing | the wolfmux block in `~/.zshrc` is read when a terminal opens; an already-open terminal has not sourced it | open a new terminal and try again |
| `teamctl <Tab>` offers nothing in a new terminal | zsh loads `compinit` late (oh-my-zsh and some frameworks run it inside their init); the completer registers only when a completion system is already loaded | the block sits at the very end of `~/.zshrc`, which is right for oh-my-zsh. A shell that never runs compinit needs `autoload -Uz compinit && compinit` above the wolfmux block |
| you use bash, not zsh | install.sh wires only the zsh shim into `~/.zshrc` | `echo 'eval "$(teamctl completion bash)"' >> ~/.bashrc` (not `source <(…)`: macOS bash 3.2 cannot source a process substitution) |
| Tab offers commands but not roles or teams | the backend resolves the project through the directory you are in | `cd` into the project (the main checkout or any of its worktrees) and try again |

## Useful one-liners

```bash
tmux -L wolfmux ls                                   # every team session on this machine
tmux -L wolfmux kill-server                          # stop all teams at once
tail -20 ~/.wolfmux/state/*/events.jsonl | jq -c .   # lifecycle log: start, spawn, stop, restart, nudge, destroy
jq . ~/.wolfmux/state/<project>/agents/<role>.json   # what teamctl knows about one agent
git worktree list && git branch --list 'ai/*'        # what git knows (default branch template)
bd list --status in_progress,blocked                 # what Beads knows
```
